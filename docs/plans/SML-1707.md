# Implementation Plan: SML-1707

## Ticket
**enhance-linear-issues: support per-project repo mapping for file links (REPO_BROWSE_URL is single-repo)**

`REPO_BROWSE_URL` is derived once from the cwd's `git remote get-url origin` (Step 2C) and applied
to every issue's file links (Linking Rules). For a batch spanning projects backed by different
repos, this produces file links pointing at the wrong codebase, and the code-reference verification
(grep/ls) only inspects the cwd repo. Fix: make file linking + verification repo-aware so off-repo
issues don't get wrong/unverified links. Single-project runs must be unaffected.

## Scope Classification
small — 1 source file (`skills/enhance-linear-issues/SKILL.md`) + 1 committed plan (`docs/plans/SML-1707.md`).

## Overview
Establish that `REPO_BROWSE_URL` and code-reference verification are **cwd-repo-scoped**, valid only
for issues whose code lives in the current working directory's repo. Single-project runs (every issue
in the cwd repo) are unchanged. For multi-project batches: use an explicitly-provided project→repo
mapping when present; otherwise skip file links / code references for off-repo issues (plain text /
"needs investigation"), consistent with the skill's existing "ONLY if verified" / "don't guess" rules.

## Approach Decision

The ticket explicitly offers two options: **(a)** map project→repo, or **(b)** skip file links / mark
them unverified when cwd ≠ the issue's repo.

**Approach A: Conservative cwd-scoping + accommodate an explicit mapping (SELECTED)**
- Document that `REPO_BROWSE_URL` and grep/ls verification only cover the cwd repo. For off-repo
  issues in a multi-project batch, use a project→repo mapping *if the run provides one*, else omit
  file links and code references (plain text / needs-investigation).
- Pros: No new config mechanism or speculative discovery; surgical (touches only the 5 sections that
  already reference REPO_BROWSE_URL); single-project path is provably unchanged → no version bump;
  fully aligned with existing Guard Rails ("ONLY if verified", "don't guess"). Satisfies both halves
  of the ticket's "map project→repo (or skip...)".
- Cons: Without a provided mapping, off-repo issues simply get no file links (acceptable — better
  than wrong links; the verification can't run for them anyway).

**Approach B: Build a full project→repo config system**
- Add a config file / auto-discovery that maps every project to a repo location and browse URL.
- Pros: Could auto-link across all repos.
- Cons: Over-engineered for a P2 follow-up. The skill has no config-file mechanism today and no
  reliable way to discover other repos' on-disk locations or remotes. Verification still can't run
  against repos that aren't checked out. Introduces speculative surface area the ticket didn't ask
  for. Rejected.

### Selection Rationale
Approach A is the minimal change that makes the behavior correct-by-construction: a link/citation is
only produced when it can be verified against an accessible repo. It honors the skill's voice and
existing guard rails, keeps single-project runs byte-identical, and leaves the door open to a provided
mapping without inventing config infrastructure. This matches the SML-1702..1706 precedent of
behavioral fixes that don't change single-project output.

### Adaptation Guidance
If, while editing, the per-issue mapping language reads as heavier than the surrounding prose, drop to
the pure-(b) form: "for issues not in the cwd repo, omit file links and code references." Non-negotiable
constraint: **the single-project path and enhancement output must not change**, so the Version stays 3.

## Risk Assessment & Edge Cases

### Risks
- Scope creep: tempting to build a config system. Mitigated by Approach A's "accommodate if provided, else skip."
- Inconsistency across the 5 cross-referencing sections. Mitigated by editing all of them in one unit and re-reading.

### Edge Cases
| Category | Edge Case | Expected Behavior | Unit |
|----------|-----------|-------------------|------|
| Common path | Single-project run (cwd == only repo) | Unchanged — all issues use cwd REPO_BROWSE_URL, verification valid | Unit 1 |
| Multi-repo, no mapping | Batch issue's code is in a different repo, no mapping provided | Omit file link / code ref; plain text or "needs investigation" | Unit 1 |
| Multi-repo, mapping provided | User supplies project→repo browse URL / checkout path | Use the per-issue mapped URL; verify only against an accessible checkout | Unit 1 |
| Git unavailable | `git remote get-url origin` fails | REPO_BROWSE_URL empty, file linking unavailable (pre-existing behavior) | Unit 1 |
| Integration invariant | Idempotency / Step 4 dedup | Version unchanged (3) → previously-stamped issues are NOT force-reprocessed | Unit 1 |

## End-to-End Narrative

After implementation, file-link emission works as follows:

1. **Skill run starts** (UNCHANGED) -> Step 2C derives the cwd `REPO_BROWSE_URL` from git origin + branch.
2. **Step 2C now records repo scope** (NEW) -> REPO_BROWSE_URL is documented as covering only the cwd
   repo; a multi-project block explains using a provided project→repo mapping, else skipping links for
   off-repo issues.
3. **Per-issue enhancement** (UNCHANGED for single-project) -> for an issue in the cwd repo, code refs
   are verified via grep/ls and file links use cwd REPO_BROWSE_URL — exactly as before.
4. **Off-repo issue in a multi-project batch** (MODIFIED) -> instead of emitting a wrong-repo link,
   the skill uses the mapped URL if provided, otherwise omits the file link / writes "needs
   investigation" and does not cite unverified code references.
5. **Linking Rules / Guard Rails / step 6** (MODIFIED) -> all now phrase file links and verification as
   "the issue's own repo," consistent with Step 2C.
6. **Large-batch sub-tasks** (MODIFIED) -> Step 5 passes the project→repo mapping alongside the repo
   browse URL; sub-tasks read the updated Linking Rules from SKILL.md and apply the same per-issue rule.

This covers AC1 (steps 2,4,5), AC2 (steps 3,4,5), AC3 (step 3 + Version unchanged), AC4 (steps 5,6).
