# Implementation Plan: SML-1701

## Ticket
**enhance-linear-issues: replace timestamp dedup with content-hash idempotency; skip no-change writes**

The skill's re-run dedup (Step 4) is broken three ways: (1) the footer is written `_..._` but Linear stores it `*..*`, so the literal-underscore grep never matches; (2) `updatedAt` is bumped by unrelated comments, so the "updatedAt within ~1min" check yields false changes; (3) pristine/NoChangesNeeded issues still get a full-description write just to append a footer (wasteful + risks corrupting `<issue>` mention tags). Fix: never write zero-change issues, and dedup via a content hash carried in a `v3` footer.

## Scope Classification
small — 1 file (`skills/enhance-linear-issues/SKILL.md`). Non-test ticket (markdown prompt content; no build/test/lint toolchain).

## Overview
Edit `skills/enhance-linear-issues/SKILL.md` to: bump the skill version 2→3; replace the timestamp/`updatedAt` dedup in Step 4 with a content-hash comparison that matches both footer forms; change the Enhancement Footer to a `v[VERSION], [TIMESTAMP], [HASH]` format written only to changed issues, computed over the post-save normalized description via a save→refetch→hash→save sequence; and make every "no content change" path a true no-op (no `save_issue`). Update all dependent sections (Enhancement Process step 4, Step 9, Guard Rails, calibration example) so no contradictory "always append footer" / `updatedAt` language survives.

## Approach Decision

Small, obvious scope — single-file prose edits to a prompt document. Rationale: the ticket prescribes the mechanism (content hash over post-save form, no-op on zero change, v3 footer). The only real design choice is **how the hash is made reproducible across Linear's markdown normalization**.

**Approach A (SELECTED): Hash the post-save normalized description (save → refetch → hash → save).**
- Faithful to the ticket's explicit instruction ("Hash the post-save/normalized form, since Linear rewrites markdown on save").
- Pros: dedup is robust against Linear's normalization; re-run hash provably matches.
- Cons: a changed issue incurs one extra `save_issue` (body, then body+footer).

**Approach B (rejected): Hash our pre-save draft and rely on our own normalization matching Linear's.**
- Pros: single write per changed issue.
- Cons: depends on perfectly mirroring Linear's (undocumented) normalization; a mismatch reintroduces false re-enhancement — the exact bug we're fixing. Ticket explicitly rejects this.

### Adaptation Guidance
Non-negotiable: re-run detection must be immune to markdown normalization, clock skew, and `updatedAt` bumps, and zero-change issues must never be written. The hash must be computed deterministically (shell `sha256sum`, not model estimation). If the two-write sequence is ever simplified, the hash MUST still cover the actually-stored form.

## Risk Assessment & Edge Cases

### Risks
- **Internal contradiction**: easy to update Step 4 but leave "always append footer" language elsewhere (Guard Rails, calibration example, Enhancement Process step 4). Mitigation: edit all 7 sites; final grep for `updatedAt` and "[Aa]lways append".
- **Two-write cost**: changed issues now cost an extra write. Accepted per ticket; net token cost still drops because pristine writes (the dominant cost) are eliminated.
- **Hash reproducibility**: if instructions let the model "estimate" a hash, dedup breaks. Mitigation: mandate a deterministic shell command.

### Edge Cases
| Category | Edge Case | Expected Behavior | Unit |
|----------|-----------|-------------------|------|
| State transition | Issue has a legacy v2 footer (`_Last enhanced: v2, <ts>_`, no hash) | Version mismatch → process normally; remove old footer; if content changes, stamp v3 hash footer; if no change, no write (footer-less) | 1 |

## End-to-End Narrative

After implementation, an enhancement run works as follows:

1. **User invokes the skill** → Step 1 announces `enhance-linear-issues v3` (MODIFIED: version is now 3).
2. **Issues gathered** (UNCHANGED).
3. **Step 4 dedup** (MODIFIED): for each issue, look for a footer matching `Last enhanced: v<n>, <ts>, <hash>` in **either** `_..._` or `*..*` form. If none or version ≠ 3 → process. If v3 footer present → strip footer + trailing blanks, `sha256sum`-hash the remainder (first 12 hex), compare to the footer's hash. Equal → **skip** (no read-heavy processing, no write). Different → process. `updatedAt` is no longer consulted.
4. **Enhancement Process** (MODIFIED step 4): if the issue is Excellent/NoChangesNeeded, make no changes and **do not write** — report skipped.
5. **Step 9 apply** (MODIFIED): unchanged issues are skipped (no `save_issue`). For a changed issue: `save_issue(body)` → `get_issue` to read normalized body → `sha256sum` first-12-hex hash → `save_issue(body + "\n\n_Last enhanced: v3, <utc>, <hash>_")` (NEW two-write sequence).
6. **Next run** (NEW behavior): the stamped issue's stored body hashes identically → Step 4 skips it. A pristine issue (never stamped) is re-analyzed but, being unchanged, is never written. A comment-bumped `updatedAt` no longer triggers re-enhancement.

All acceptance criteria (AC1–AC5) are covered by steps 3–6.
