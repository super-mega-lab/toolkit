# Implementation Plan: SML-1703

## Ticket
**enhance-linear-issues: safety review should flag token loss, not raw length/edit-distance**

The Step 7 Safety Review flags "description >20% shorter" and "title edit distance >50%". In auto mode FLAG = silently skipped, so the skill's best edits (tightening bloated descriptions, fixing bad titles) get auto-dropped — the quality goal fights its own guardrail. Replace the raw-metric checks with a token-preservation check that flags only when high-value tokens (links, image/screenshot refs, issue IDs, verified code refs) present in the original are missing from the proposal.

## Scope Classification
small — 1 file (`skills/enhance-linear-issues/SKILL.md`) + this plan doc.

## Overview
Rewrite the Step 7 Safety Review table: drop the two raw-metric rows ("Description shrinkage", "Title radical change"), fold the existing "Data loss" row into a broader "Token loss" row covering links, image/screenshot refs, issue IDs, and verified code references, and add one framing sentence stating that intentional shortening and title rewrites are allowed when those tokens survive. Keep the three structural rows (Invalid team, Orphaned sub-issues, Circular relations) and the Auto/Preview mode notes unchanged.

## Approach Decision

Small, obvious change — single rationale rather than a comparison matrix.

**Selected:** Replace the two raw-metric rows with one consolidated "Token loss" row (which subsumes the old "Data loss" check, since screenshots+links ⊂ the token set), plus a one-sentence intro framing the intent. This is the minimal edit that satisfies the ticket: it removes exactly the two offending checks, generalizes data-loss detection to the full token set the ticket names, and makes the "shortening/rewrites are allowed" intent explicit without adding redundant prose.

**Rejected:** (a) Keeping a separate "Data loss" row alongside a new "Token loss" row — redundant, since Token loss is a strict superset. (b) Adding both an intro paragraph and a trailing paragraph restating the policy — redundant per the simplicity guideline; one framing sentence + the self-explanatory table row suffices.

### Adaptation Guidance
Non-negotiable: the four token categories from the ticket (links, image/screenshot refs, issue IDs, verified code refs) must all appear in the fail condition, and the two raw-metric checks must be gone. Match the skill's existing intro-sentence-then-table style.

## Version Decision
Keep `Version: 3` (no bump). The version gates the Step 4 idempotency/"already-processed" filter; this change is to the Step 7 safety review (approval/apply flow), not the dedup mechanism, footer format, hash method, or enhancement content. Matches precedent: SML-1702 (decomposition-gate approval-flow change) kept v3; SML-1700 (behavioral fix) kept v3; SML-1701 bumped only because it changed the dedup mechanism itself. Flagged-and-skipped proposals never get a footer, so they re-process on the next run regardless of version — no bump is needed to re-catch them.

## End-to-End Narrative
After implementation, the enhance-linear-issues skill's Step 7 works as follows:

1. **An enhancement proposal is produced** (UNCHANGED) → Step 6 collects title/description proposals.
2. **Safety Review runs** (MODIFIED) → instead of flagging proposals that are >20% shorter or whose title changed >50%, it runs the Token loss check: it compares the original's high-value tokens (links, image/screenshot refs, issue IDs, verified code refs) against the proposal and FLAGs only if one is dropped.
3. **A tightened/retitled proposal that preserves all tokens** (NEW behavior) → now PASSES rather than being FLAGged-and-skipped.
4. **A proposal that drops a link or screenshot** (UNCHANGED intent, MODIFIED mechanism) → still FLAGged (Token loss subsumes the old Data loss check).
5. **Auto mode applies passing proposals, skips flagged** (UNCHANGED) → mode notes unchanged.

This covers AC1–AC4: the two raw-metric checks are removed (steps 2–3), the token-preservation check is added (steps 2,4), and shortening/retitling is allowed when tokens survive (step 3).
