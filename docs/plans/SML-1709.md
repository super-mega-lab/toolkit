# Implementation Plan: SML-1709

## Ticket
**enhance-linear-issues: hash the refetched bytes, not a reconstructed body, in save-then-rehash**

The content-hash footer's save-then-rehash sequence must hash the *exact* description string returned by the Step-2 `get_issue` refetch — not a hand-authored body that predicts Linear's markdown normalization. A single mispredicted normalization (`_`→`*`, autolink, entity-escaping) would produce a footer hash that never matches on re-run, silently breaking idempotency (the issue gets re-enhanced forever).

## End-to-End Narrative

After this change, the footer save-then-rehash works as follows:

1. **Issue with content changes reaches the footer step** (UNCHANGED) -> save enhanced body without footer (step 1).
2. **Refetch via `get_issue`** (UNCHANGED) -> returns Linear's normalized stored description (step 2).
3. **Hash the refetched bytes** (MODIFIED) -> step 3 now explicitly requires hashing the *exact* string returned by step 2 (write verbatim to temp file or pipe straight to `sha256sum`), and forbids hashing a reconstructed/predicted body. Algorithm (SHA-256, first 12 hex) and example command unchanged.
4. **Capture UTC timestamp** (UNCHANGED) -> `date -u` (step 4).
5. **Append footer and save once more** (UNCHANGED) -> `v3 + timestamp + hash` (step 5).
6. **Later re-run dedup** (UNCHANGED) -> Step 4 strips footer, rehashes the (already-normalized) body, matches → skip. Now guaranteed correct because the stored hash was computed over the actual stored bytes.

All four acceptance criteria are addressed by the single step-3 rewrite.
