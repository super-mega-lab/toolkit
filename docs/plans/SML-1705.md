# Implementation Plan: SML-1705

## Ticket
**enhance-linear-issues: skip full-workspace load (teams/projects) for single-issue runs**

Step 2B unconditionally calls `list_teams` + `list_projects` (~11–12 KB each) for every run, even when the user targeted a single issue. For a single targeted fix, team-reassignment and decomposition rarely apply, so the full-workspace discovery is mostly wasted tokens. Gate it to multi-issue / organize-triage requests; for a single issue, use the team/project already returned by `get_issue`.

## Scope Classification
small — 1 source file (`skills/enhance-linear-issues/SKILL.md`) + 1 repo plan (`docs/plans/SML-1705.md`).

## Overview
Make the Step 2B workspace-context discovery conditional on request scope, preserve the Linear-MCP-availability guard (relocated so it keys off whichever Linear call runs first), and update the Step 3 scope display so a single-issue run doesn't imply a full team/project list was loaded.

## Approach Decision

Small, obvious content edit — short rationale rather than a full table.

### Considered Approaches
**Approach A: Conditional gate inside Step 2B + graceful Step 3 display (SELECTED)**
- Rewrite Step 2B section B into two branches (multi-issue/triage → full discovery; single targeted issue → use `get_issue`'s own team/project, with an on-demand fallback). Move the MCP-availability guard to a general note. Make Step 3's two "Available …" lines conditional.
- Pros: Minimal, surgical, matches the ticket's exact ask and its "Refs: Step 2B" pointer. Preserves correctness (MCP guard + on-demand fallback). Keeps Step 2's parallel-execution structure (gate decided from request form, not from fetch results).
- Cons: Slightly longer Step 2B prose.

**Approach B: Add a separate "scope detection" step before Step 2**
- Pros: Centralizes single-vs-multi decision.
- Cons: Larger structural change, more renumbering risk, over-engineered for a one-call gate. Rejected.

### Selection Rationale
Approach A is the smallest change that fully satisfies the ticket and stays within the section the ticket names (Step 2B). It preserves the two correctness invariants (MCP-availability guard; ability to still reassign teams when genuinely needed via on-demand fetch).

### Adaptation Guidance
If gating purely on request form proves ambiguous, fall back to: run full discovery whenever more than one issue is in scope OR the request is organize/triage-style; otherwise skip. Non-negotiable: a single targeted-issue run must NOT call `list_teams`/`list_projects` by default, and the MCP-unavailable stop condition must remain reachable.

## Risk Assessment & Edge Cases

### Risks
- Removing the MCP-availability guard's home (the `list_teams` call) could lose the "stop if MCP down" behavior for single-issue runs. Mitigated by relocating the guard to key off the first Linear call (Step 2A `get_issue`/`list_issues`).
- Over-gating could break legitimate single-issue team reassignment. Mitigated by an on-demand fetch fallback note.

### Edge Cases
| Category | Edge Case | Expected Behavior | Unit |
|----------|-----------|-------------------|------|
| Boundary | Filter request that returns exactly 1 issue | Treated as multi-issue intent (filter/triage form) → full discovery still runs; acceptable | 1 |
| Error path | Linear MCP unavailable on a single-issue run | Step 2A `get_issue` fails → skill stops with the MCP-unavailable message | 1 |
| State transition | Single-issue run later needs team reassignment | On-demand `list_teams`/`list_projects` fetch at that point | 1 |
| Integration invariant | Large batch (>10 issues) | Full discovery runs as before; sub-task context (line 136) still populated | 1 |

## End-to-End Narrative

After implementation, a **single targeted-issue** run ("clean up SML-1705") works as follows:

1. **User request names one issue by ID/URL** (UNCHANGED) -> Step 1 announces version, detects mode.
2. **Step 2A fetches the issue** via `get_issue` (UNCHANGED) -> returns the issue including its own team/teamId (and project if set).
3. **Step 2B gate** (NEW) -> recognizes a single targeted issue → SKIPS `list_teams`/`list_projects`; uses the issue's own team/project from step 2.
4. **MCP-availability** (MODIFIED) -> verified by the Step 2A fetch; if it failed, the skill already stopped with the MCP-unavailable message.
5. **Step 3 scope confirmation** (MODIFIED) -> shows the issue's own team/project (not a full workspace list).
6. **Steps 4–9** (UNCHANGED) -> dedup, enhance, safety review, apply — identical output and footer/hash behavior (version stays v3).

A **multi-issue / organize-triage** run is UNCHANGED: Step 2B runs full `list_teams` + `list_projects`, Step 3 shows the full lists, large batches still get the team/project lists in sub-task context.

All four acceptance criteria (AC1–AC4) are covered by steps 3–5.
