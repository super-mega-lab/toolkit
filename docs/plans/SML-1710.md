# Implementation Plan: SML-1710

## Ticket
**enhance-linear-issues: clarify whether single-issue runs may fetch parent/sibling context (Step 2B)**

Step 2B says a single targeted issue should skip the full-workspace load and use only the issue's own team/project. In practice, 4 of 6 recent single-issue runs (SML-1693/1694/1695/1697) also fetched the **parent issue and its siblings** (via `get_issue` / `list_issues`) for related-link and decomposition context. That is scoped and defensible (no workspace dump — the SML-1705 win still holds), but it goes slightly beyond the literal spec, which is currently silent on parent/sibling fetches. Pick one deterministic rule.

## Scope Classification
small — 1 source file (`skills/enhance-linear-issues/SKILL.md`) + 1 repo plan (`docs/plans/SML-1710.md`).

## Overview
Amend Step 2B section B's "Single targeted issue" bullet to **explicitly sanction bounded, on-demand parent/sibling context fetches** for single-issue runs — mirroring the on-demand `list_teams`/`list_projects` fallback already in that bullet — and bound them so the SML-1705 no-workspace-dump win holds. Pure instruction-text clarification; no change to enhanced output, footer/hash/dedup, or the teams/projects gate.

## Approach Decision

Small, obvious content edit — short rationale rather than a full table.

### Considered Approaches
**Approach A: Sanction bounded on-demand parent/sibling fetches (SELECTED)**
- Append a clause to the Step 2B "Single targeted issue" bullet that explicitly permits, on demand, fetching the issue's parent (`Linear:get_issue` with `includeRelations`) and a bounded set of siblings/related issues (a single targeted `Linear:list_issues` call) for related-link/decomposition context — bounded to a few targeted calls, no full-workspace dump, no recursive tree traversal.
- Pros: Behavior-preserving (4/6 recent runs already do this); consistent with the existing on-demand teams/projects fallback in the same bullet and with Enhancement-Process step 6 (which already mandates a related-issue search); keeps the SML-1705 token-savings win intact (teams/projects stay gated); surgical (one bullet).
- Cons: Slightly longer Step 2B prose.

**Approach B: Forbid parent/sibling fetches on single-issue runs**
- Pros: Maximally minimal Linear I/O.
- Cons: Regresses current useful behavior; contradicts Enhancement-Process step 6 ("Search for related issues via `list_issues`") and the "Link related issues" DO; the author frames current behavior as "scoped and defensible." Rejected.

### Selection Rationale
Approach A is the deterministic resolution the ticket's framing points to ("scoped and defensible", "the SML-1705 win still holds"). It is behavior-preserving and consistent with the rest of the skill (the on-demand teams/projects fallback right above it, and the related-issue search in step 6). Forbidding would create a contradiction with step 6 and remove value with no token win of consequence.

### Adaptation Guidance
Non-negotiable invariants if the exact wording below reads awkwardly: (a) Step 2B must explicitly address parent/sibling fetches (no longer silent); (b) it must pick the **sanction** rule, not forbid; (c) the sanction must be **bounded** — a few targeted `get_issue`/`list_issues` calls, explicitly NOT a workspace dump (`list_teams`/`list_projects` stay gated) and NOT recursive traversal; (d) no change to version, footer/hash/dedup, or the teams/projects gate.

**Proposed wording** (append to the "Single targeted issue" bullet, after the existing teams/projects on-demand sentence):

> Scoped **parent/sibling context fetches are permitted on demand**: when an issue's related-link or decomposition assessment genuinely needs it, you may fetch its parent (`Linear:get_issue` with `includeRelations`) and a bounded set of its siblings/related issues (a single targeted `Linear:list_issues` call) — the Enhancement Process (step 6) already runs a related-issue search. Keep this bounded: a few targeted `Linear:get_issue`/`Linear:list_issues` calls, never a full-workspace dump (`list_teams`/`list_projects` stay gated as above) and never recursive tree traversal, so the SML-1705 token-savings win holds.
