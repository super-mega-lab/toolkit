# Implementation Plan: SML-1706

## Ticket
**enhance-linear-issues: batch issues per subagent in the >10 path (stop duplicating skill body per issue)**

For batches >10, the skill currently dispatches one sub-task PER issue, each prompt embedding the
full static instruction block (~250 lines: Enhancement Calibration + Decomposition + Guard Rails +
Linking + Footer) plus dynamic context, and each sub-task independently runs fuzzy `list_issues`
related-searches. At 20–30 issues this multiplies input tokens. Fix: (1) batch several issues per
sub-task, (2) factor the static block into a reference sub-tasks read once, (3) share one
related-issue search across the batch.

## Scope Classification
small — 1 file (`skills/enhance-linear-issues/SKILL.md`). Plus the auto-generated `docs/plans/SML-1706.md`.

## Overview
Rewrite only the "Large batches (>10 issues)" portion of **Step 5: Process Issues** so it (a) chunks
issues into groups per sub-task, (b) tells each sub-task to read the static sections from this
SKILL.md file once instead of embedding them, and (c) runs one shared related-issue search whose
deduped candidate pool is handed to the sub-tasks. A one-line addition to Enhancement Process step 6
makes sub-tasks consume that shared pool instead of each calling `list_issues`.

## Approach Decision

### Considered Approaches
**Approach A: In-place rewrite of Step 5 large-batch; sub-tasks read static sections from this SKILL.md by path (SELECTED)**
- Keep all static sections where they are. Change only the large-batch dispatch spec (and one bullet
  in Enhancement Process). Sub-tasks are pointed at this SKILL.md (absolute path passed by the
  orchestrator; `Glob("**/enhance-linear-issues/SKILL.md")` when developing in-repo) and Read the
  named sections once.
- Pros: minimal/surgical; preserves the "single source of truth" SKILL.md; ≤10 path untouched; no
  prose cross-references break; no version bump; mirrors auto-dev's own "Read a reference file by
  pattern" convention.
- Cons: sub-tasks Read a file that also contains workflow steps not relevant to them — mitigated by
  naming the exact sections and telling them they are proposal-only sub-tasks.

**Approach B: Physically extract the static block into `skills/enhance-linear-issues/references/enhancement-reference.md`**
- Move Enhancement Process, Calibration, Decomposition, Guard Rails, Linking, Footer, Output Format
  into a new reference file; SKILL.md and sub-tasks both point at it.
- Pros: literal "factor into a reference"; sub-task reads only relevant content; matches `references/`
  layout used by auto-dev.
- Cons: large restructure of an interleaved workflow; those sections sit between Phase 1 and Phase 2
  and are referenced by prose ("see the Enhancement Footer section", Step 4/7/8/9), so extraction
  breaks several internal references and risks regressions — disproportionate for a P2 doc refinement.

### Selection Rationale
Approach A satisfies all three fix bullets while touching the fewest lines and preserving every
existing cross-reference and the ≤10 path. The ticket's "reference the subagents read once" is met by
having sub-tasks Read the existing SKILL.md once (the established in-repo pattern) rather than
embedding the block per prompt. Approach B's extraction cost/regression risk is not justified for a
latent, unmeasured P2 cost.

### Adaptation Guidance
If pointing sub-tasks at the SKILL.md path proves unreliable in a given install, fall back to having
the orchestrator write the static sections to ONE shared file at the start of the >10 path and pass
that single path to all sub-tasks (still read-once, still O(1) not O(N)). Non-negotiable constraint:
the enhancement OUTPUT, the footer/hash machinery, Step 4 dedup, and the Version number must remain
byte-for-byte unchanged.

## End-to-End Narrative

After implementation, a >10-issue enhancement run works as follows:

1. **Step 5 reached with >10 issues** (UNCHANGED) → orchestrator selects the large-batch strategy.
2. **Shared related-issue search** (NEW) → orchestrator collects search terms from all batch issues,
   issues ONE `Linear:list_issues` pass, dedups, and builds a candidate related-issue pool
   (IDs + titles).
3. **Chunking** (NEW) → orchestrator partitions the issues into chunks of ~5.
4. **Dispatch per chunk** (MODIFIED) → one sub-task per chunk (was: one per issue). Each sub-task
   prompt carries only the chunk's issue IDs, dynamic context (workspace slug, repo URL, team/project
   lists, batch issue list), the shared related-issue pool, and a pointer to this SKILL.md.
5. **Sub-task reads static block once** (NEW) → the sub-task Reads the Enhancement Process,
   Enhancement Calibration, Decomposition Criteria, Guard Rails, Linking Rules, Enhancement Footer,
   and Output Format sections from this SKILL.md a single time, then processes every issue in its chunk.
6. **Per-issue analysis** (MODIFIED) → for related issues, the sub-task matches against the shared
   pool instead of running its own `list_issues` search; everything else in Enhancement Process is
   unchanged. Sub-tasks return Output-Format proposals.
7. **Phase 2 apply** (UNCHANGED) → orchestrator collects proposals, runs Safety Review, gets approval,
   and applies with the content-hash footer.

All acceptance criteria are covered: AC1 (step 3–4), AC2 (step 4–5), AC3 (step 2 + 6), AC4 (no
change to steps 7 / footer / version / the ≤10 path).
