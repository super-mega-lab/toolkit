# Implementation Plan: SML-1704

## Ticket
**enhance-linear-issues: require explicit UTC timestamp (`date -u`) for the footer**

The footer timestamp is sometimes fabricated. In one real run (SML-1667/1629) the skill never called `date -u` and stamped a rounded placeholder `...T00:00:00Z`, misrepresenting when it ran. Two other runs did call `date -u` and got precise times — the behavior is inconsistent. Fix: make "get current UTC time via `date -u`" an explicit, required step before writing the footer. Never infer or round.

## Scope Classification
small — 1 source file (`skills/enhance-linear-issues/SKILL.md`) + 1 plan doc (`docs/plans/SML-1704.md`).

## Overview
The skill's "Enhancement Footer" section already mandates that the `[HASH]` be computed in the shell ("never estimate it"), but the `[TIMESTAMP]` is only described loosely as "UTC timestamp." That asymmetry is the root cause: the model is free to fabricate/round the time. The fix applies the same shell-capture rigor to the timestamp by adding an explicit, required `date -u` step to the save-then-rehash sequence and tightening the footer Rules.

## Approach Decision

This is a content/prompt edit with one obvious approach: mirror the existing HASH treatment for the TIMESTAMP. The skill already has a 4-step "save-then-rehash sequence" where step 3 computes the hash in the shell. The cleanest, most discoverable place to force a real timestamp is a sibling required step in that same sequence (the timestamp is consumed by the very next step, the final footer-stamping save). Rationale: it sits exactly where the value is used, it parallels the hash's "never estimate it" language the model already follows, and it keeps the change surgical (no new section, no format change). Adaptation guidance: if a reviewer prefers the directive live only in the Rules list, the new step can be collapsed into the Rules bullet — but the non-negotiable requirement is that obtaining the time via `date -u` is stated as a *required action*, not a passive description.

## Invariants to Preserve
- **Footer format unchanged:** `_Last enhanced: v[VERSION], [TIMESTAMP], [HASH]_`. The fix changes how the timestamp is *obtained*, not the format — so existing v3 footers and the hash-based dedup (Step 4) remain valid.
- **Version stays at 3.** This change does not affect the Step 4 "already-processed" dedup (which hashes the footer-stripped body, independent of the timestamp value). Bumping would force needless re-processing of all v3-stamped issues. Matches SML-1702/1703 precedent.
- **Hash treatment untouched:** the SHA-256 / `sha256sum | cut -c1-12` shell step stays exactly as-is.
- **No new dependencies.** `date -u` is a POSIX coreutil already assumed by the skill's git/`sha256sum` shell usage.

## End-to-End Narrative

After implementation, stamping a changed issue's footer works as follows:

1. **Issue has content changes** (UNCHANGED) -> enhancement produces a new body.
2. **Save body without footer** (UNCHANGED) -> `Linear:save_issue(id, description=<enhanced body>)`.
3. **Re-fetch normalized body** (UNCHANGED) -> `Linear:get_issue`.
4. **Hash normalized body in shell** (UNCHANGED) -> `sha256sum <file> | cut -c1-12`.
5. **Capture real UTC time in shell** (NEW) -> `date -u +'%Y-%m-%dT%H:%M:%SZ'`; never inferred or rounded.
6. **Append footer and save** (MODIFIED) -> uses the exact timestamp from step 5 and hash from step 4; format `_Last enhanced: v[VERSION], [TIMESTAMP], [HASH]_` is unchanged.

This covers AC1 (step 5 is explicit/required), AC2 (no-fabrication language + named `...T00:00:00Z` failure), and AC3 (Rules bullet references `date -u`; example de-rounded).
